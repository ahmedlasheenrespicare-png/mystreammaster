## 5. مسار إعادة البناء والنشر بعد تحديث الأرشيف (القسم 4.4)

- **المشكلة السابقة**: التزام `fixtures-archive.yml` يحمل `[skip ci]` ويُدفع بواسطة `GITHUB_TOKEN`، فلا يُشغّل `deploy.yml`، مما يترك الموقع الحي دون إعادة بناء عند تغيّر ملفات الأرشيف.
- **الحل المنفّذ**:
  1. تحسب مهمة `publish` في `.github/workflows/fixtures-archive.yml` عدد الملفات المتغيرة دلالياً (`changedFiles`) وآخر وقت جلب (`lastFetchedAt`) عبر `publish-fixtures-archive.mjs`.
  2. إذا لم تتغير أي بيانات دلالية (`git diff --cached --quiet`)، تضبط `changed=false` وتتوقف دون التزام ودون تشغيل النشر (منع النشر المتكرر بلا تغير).
  3. إذا تغيرت ملفات الأرشيف على الفرع `main`، تلتزم بـ `[skip ci]` (لمنع أي حلقة لانهائية مع أحداث `push`) ثم تستدعي وظيفة `deploy` في `fixtures-archive.yml` ملف `.github/workflows/deploy.yml` عبر `workflow_call` بشرط `needs.publish.outputs.changed == 'true' && github.ref == 'refs/heads/main'`.
  4. يحتفظ `deploy.yml` بجميع حراس السلامة والاختبارات (`concurrency: group: deploy-hostinger`, `npm ci --prefix website`, `npm run typecheck && npm test && npm run build`, `SamKirkland/FTP-Deploy-Action@v4.3.5`) ويطبع تقرير الحداثة الزمني (`lastFetchedAt`، `lastDeployedAt`، و`deltaSeconds`).
