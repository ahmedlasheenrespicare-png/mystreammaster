## تشغيل آمن ومراجعة الشروط والخطط

- cron يومي `03:17 UTC`؛ نافذة UTC شاملة اليوم −30 إلى اليوم +14 = **45 يوماً**.
- التفعيل لا يتم بمجرد الدمج. بعد مراجعة شروط المصادر وتوثيق الإذن وحدود الحساب، اضبط Repository Variables:
  - `FIXTURES_SOURCES_APPROVED=true`: إقرار مراجعة المصادر، وإلا تُسجّل البطولات `SOURCE_TERMS_REVIEW_REQUIRED` دون اتصال.
  - `HIGHLIGHTLY_PLAN_APPROVED=true`: فقط بعد تأكيد سعة الخطة، وإلا يُحفظ المصري السابق دون طلبات.
  - `FIXTURES_STATISTICS=true`: اختياري للمرحلة الثالثة فقط، يزيد الطلبات. الافتراضي معطّل.
- المفتاح `HIGHLIGHTLY_API_KEY` في GitHub Secrets فقط؛ يُمرر لمهمة الجمع وحدها، لا للمصنوعات أو المتصفح أو مهمة الكتابة. لا يلزم مفتاح ESPN.
- لم تُراجع شروط ESPN غير الرسمية أو Highlightly مراجعة قانونية من هذه البيئة، ولم يُثبت السماح بتخزين/إعادة نشر هذه البيانات. مراجع المالك للمراجعة: `https://disneytermsofuse.com/`، `https://highlightly.net/` ووثائق/لوحة حساب Highlightly وعقد الخطة الفعلي. هذه روابط مراجعة، لا ادعاء بالسماح أو بحصص مجانية معينة.
- المستودع **خاص** بحسب `gh repo view`. قراءة إعدادات Actions أعادت HTTP 403 (نطاق صلاحيات التطبيق)، لذلك لم يمكن تأكيد الدقائق/الفوترة/السعة. على المالك مراجعة Settings → Billing and licensing → Usage وSettings → Actions → General قبل التفعيل.
- الحد الأساسي النظري عند نجاح كل أيام ESPN: 11 ×45 = **495 طلب ESPN**، والمصري **45 طلباً على الأقل** (مع صفحات إضافية لكل يوم يتجاوز 100 مباراة). الإحصائيات تضيف طلباً لكل مباراة منتهية للدوريات الخمسة ضمن النافذة. هذه أعداد للسكربت، وليست حدود خطة المصدر.
- الطلبات متسلسلة بفاصل 1.1 ثانية، ومهلة 20 ثانية للطلب؛ لا تكرار فوري بعد 429. فشل أي يوم/صفحة يرفض تحديث البطولة كلها. الوقت الأساسي الأدنى لفواصل 540 طلباً نحو 10 دقائق، ويزيد مع الشبكة والتفاصيل؛ سقف مهمة الجمع 45 دقيقة. عند timeout لا تُنشر ملفات جزئية بلا تقرير مكتمل.

## التحقق والكتابة

- ملفات `website/src/content/fixtures-archive/<league>/<source-season>.json`؛ الموسم من المصدر، لا تخمين حسب الشهر. تحتفظ الأرشفة بالمباريات القديمة خارج النافذة ولا تحذفها.
- التحقق من المعرّفات، المصدر، الفرق، التوقيت UTC، النتيجة، الحالة، الحضور والقيم الإحصائية. لا يُستنتج الإنهاء من وجود نتيجة وحدها. الحقول غير المتوفرة `null` وتظهر «غير متاح». النتيجة الافتراضية الصفرية للمباراة المجدولة لا تُحفظ كنتيجة حقيقية. الحضور الصفر كما أرسله المصدر يُحفظ مع تنبيه أنه ليس تأكيد حضور قبل المباراة.
- رفض التكرار، الاقتطاع (500 حدث ESPN في يوم)، عدد مباريات غير معقول، pagination غير مكتمل أو متغير، موسم مفقود أو معرّف غير مطابق. النافذة الفارغة لا تستبدل نسخة سابقة بملف فارغ.
- فشل بطولة لا يمنع حفظ البطولات الناجحة، لكنه ظاهر في التقرير وتحذير التشغيل. الملفات المرشحة لا تُعتمد إلا للبطولات الناجحة.
- مهمة `collect` قراءة فقط، و`publish` كتابة مستقلة بلا أسرار المصادر. **GitHub لا يتيح `contents: write` على مستوى الخطوة**؛ الفصل بمهمتين هو أقرب تطبيق آمن. مهمة النشر تعيد التحقق من المصنوع كله وتمنع حذف أي معرّف تاريخي ثم تستخدم rename للملفات، والتزام Git هو وحدة النشر. لا push بالقوة، وأي اختلاف في SHA قبل الحفظ يرفض النشر القديم.
- لا التزام إذا لم تتغير القيم؛ `fetchedAt` للمباراة يحتفظ بوقت آخر تغير دلالي، ووقت محاولة الجلب الأحدث في تقرير المصنوع. الالتزام يحمل `[skip ci]` كما طُلب.
- بسبب `[skip ci]` **لن يشغّل التزام البيانات وحده deploy.yml**. العرض ثابت داخل HTML/JS عند البناء التالي؛ يلزم تشغيل Deploy to Hostinger يدوياً لنشر أحدث الأرشيف، أو الاتفاق على ربط نشر مستقل لاحقاً. لم يُعدّل هذا PR نشر الإنتاج أو إعدادات حساب GitHub.

## العرض والإحصائيات

- صفحات البطولات تعرض الأرشيف من استيرادات محلية وقت البناء؛ المكون لا ينفذ `fetch` ولا يستدعي المصدر/ملف JSON من المتصفح. لوحة المباريات الحية وجدول الترتيب القائمان ما زالا مستقلين ويطلبان وسيط الموقع كما كانا؛ هذا PR لا يدّعي تحويل الموقع كله إلى وضع بلا شبكة.
- معدلات الهجوم/الدفاع من جدول الترتيب الحالي: الأهداف ÷ لعب، تشمل كل المتعادلين، ولا يصدر تصنيف أقوى/أضعف إذا كانت بيانات فريق ناقصة أو لعب=0. النقاط والمراكز وفارق الأهداف تُعرض من الجدول نفسه دون إعادة ترتيب بمعايير مخمّنة.
- داخل/خارج الملعب، ف/ت/خ، نظافة الشباك وسلاسل النتائج الحالية تُحسب زمنياً من النتائج المنتهية المتاحة فقط، لكل موسم؛ ليست إجمالي الموسم وليست ضماناً لسلسلة كاملة خارج النافذة. المباريات ذات النتائج الناقصة لا تدخل العد.
- الحضور وتفاصيل الاستحواذ/التسديدات/دقة التمرير تظهر لكل مباراة. جامع summary اختياري ومقيد بالدوريات الخمسة ويطابق معرّف المباراة والبطولة والفريقين. فشل التفاصيل لا يهدم الأرشيف الأساسي؛ يحتفظ بآخر تفاصيل محفوظة إن وجدت. محول التفاصيل وHighlightly اختُبرا بعينات اصطناعية في الاختبارات فقط؛ يجب تأكيد شكل الاستجابة الحية قبل اعتماد المرحلة الثالثة.
- المرحلة الرابعة غير منفّذة؛ لا توسيع لقائمة البطولات دون اتفاق.

## الحجم والأداء

- قبل التغيير: `.git` قرابة **95 MiB**، والمحتوى الحالي قرابة **620 KiB** (`du -sh`؛ أرقام مساحة قرص تقريبية لا حجم clone مضغوط).
- ملفات مباريات الإنتاج الجديدة عند إعداد التقرير: **0 ملف / 0 بايت**، لعدم وجود جلب موثّق بعد. README فقط داخل مجلد الأرشيف. حجم الإضافة البرمجية موضح في PR و`git diff --stat`، ولا يشمل مخرجات البناء المحلية.
- ناشر الأرشيف يقيس الحجم المتوقع ويرفض الكتابة إذا تجاوز مجلد الأرشيف **50 MiB**؛ يطبع الحجم وعدد الملفات عند النجاح. لا يزيل المواسم القديمة تلقائياً. مراجعة تخزين خارجي مطلوبة قبل هذا الحد؛ تاريخ Git قد يكبر أسرع من الحجم الحالي بسبب تغير JSON.
- الاستيرادات الحالية تضم الأرشيف في حزمة العميل أيضاً؛ يلزم قياس حجم JS/HTML وزمن البناء مع بيانات حقيقية قبل التوسع. حد 50 MiB حماية للمستودع وليس وعداً بأداء جيد للمتصفح. التخزين الخارجي مستقبلاً يجب أن يُستهلك وقت البناء لا من المتصفح.

## قائمة ما يلزم قبل الدمج/النشر

1. مراجعة ناتج مسبار السعودية من Actions؛ إن فشل، اختيار مصدر يعمل وإثبات معرّفه قبل تعديل وسيط المباريات الحي. لا يُعتبر هذا الطلب منجزاً قبل ذلك.
2. مراجعة شروط ESPN وHighlightly وحصة الحساب المجانية ودقائق Actions وتسجيل الموافقات.
3. تشغيل جمع فعلي بعد الموافقات، مراجعة تقرير كل بطولة والمواسم وعدد المباريات وحجم الملفات، ومطابقة عينات مع المصدر.
4. تأكيد شكل summary وHighlightly الحي، ثم تفعيل تفاصيل المرحلة الثالثة عند الحاجة.
5. نشر وإعادة بناء صريحان لرؤية أحدث الأرشيف؛ لا دمج لهذا PR تلقائياً.
